---

## 1. 方針

**バケットは 1 本のみ**（`brightstar-hr-dev-603319838936`）とし、プレフィックスで用途を分ける。

理由：バケットを分けると、ライフサイクル・暗号化・パブリックアクセスブロックの設定を**複数箇所で維持**することになり、設定漏れの事故が起きやすい。本システムは保管対象が「社員が提出したファイル」の一種類に集約されるため、1 バケット + プレフィックス分割で十分。

社員の提出物は **氏名・勤務実績・通勤経路・住所を含む個人情報**である。したがってバケットは**完全非公開を前提**とし、配布は署名付きの一時 URL でのみ行う（§4）。

---

## 2. バケット設定（2026-09-19 実測）

| 項目 | 値 | 理由 |
|---|---|---|
| バケット名 | `brightstar-hr-dev-603319838936` | 名前がグローバル一意である必要があるためアカウントIDを付加 |
| 所有スタック | `BrightstarHr-dev`（人事） | 提出物の基盤を人事スタックに集約。社員が書き、総務が読む |
| パブリックアクセスブロック | **4項目すべて有効** | 個人情報を含むため公開経路を構造的に塞ぐ |
| 既定暗号化 | **SSE-S3（AES-256）** | KMS CMK は使わない（[BS_INF-08](BS_INF-08_SSM・暗号化設計書.md) §2） |
| バージョニング | **有効** | 提出物の上書き（再提出）と誤削除からの復旧手段。旧版が残る |
| 転送中の暗号化 | HTTPS のみ（Lambda・署名付き URL とも） | |

## 3. オブジェクトレイアウト

```
hr/{yyyy}/{mm}/worktimes/  勤務表（{社員番号}_{氏名}）_{YYYYMM}.xlsx
hr/{yyyy}/{mm}/expenses/   交通費経費【{YYYY}年{MM}月{社員番号}_{氏名}】.xlsx
hr/{yyyy}/{mm}/others/     {用途}_{氏名}_{period}_{ts}.{ext}
hr/template/               配布用テンプレート（勤務表.xlsx / 交通費経費.xlsx）
pending/                   チェック不合格ファイルの一時退避
exports/                   一括DL の ZIP・CSV 出力
```

### 3.1 ファイル名の設計

| 項目 | 設計 | 理由 |
|---|---|---|
| アップロード時の元ファイル名 | **使わない**。システムが付け直す | 社員が任意の名前で送ってくるため、そのままでは整理できない。また同名衝突が起きる |
| 社員番号をファイル名に含める | 含める | **同姓同名の取り違えを防ぐ**。氏名だけでは一意にならない |
| 格納する年月 | **ファイルの中身から判定**（勤務表＝J1「年」/ L1「月」、交通費＝B1）。読めない場合は提出月 | 月末締めの書類が翌月頭にずれ込んでも、**書類に書かれた月**のフォルダに入る |

### 3.2 上書きの扱い

| ケース | 上書き | 理由 |
|---|---|---|
| 同一社員・**別の月** | されない | 年月がパスとファイル名の両方に入るため、キーが別になる |
| 同一社員・**同月・同種別** | **される** | 「再提出＝最新が有効」という業務ルールの実装。バージョニングにより旧版は S3 に残る |
| その他経費 | されない | ファイル名にタイムスタンプを含め、月内複数件の提出を許す |

## 4. 配布経路（署名付き短縮 URL）

LINE のボタンに設定できる URL は **1000 文字まで**だが、S3 の署名付き URL はこれを超えることがある。そのため**2段構え**にしている。

```
LINE のボタン
  → Lambda Function URL  GET /dl?key=<S3キー>&sig=<HMAC>
      ① sig を HMAC-SHA256（鍵＝LINE チャネルシークレット）で検証
      ② S3 presigned URL（有効期限 1 時間）を発行して 302 リダイレクト
  → S3 から直接ダウンロード
```

| 項目 | 設計 | 理由 |
|---|---|---|
| 署名アルゴリズム | HMAC-SHA256、先頭16桁（64bit） | 鍵は SSM SecureString の LINE チャネルシークレットを流用 |
| 署名対象 | **S3 キーのみ** | — |
| S3 presigned URL の有効期限 | 3600 秒 | |

### ⚠️ 設計上の弱点（§6 課題1）

署名対象に**有効期限が含まれていない**ため、`/dl` のリンク自体は**失効しない**。URL を知る者は誰でもダウンロードできる。

ただし `/dl` が指す先は**すべて `exports/` 配下**（ZIP・CSV）であり、ライフサイクルで **3 日後に自動削除**される。したがって実際の露出期間は最大 3 日に限定される。それでも、LINE メッセージの転送・端末の閲覧履歴・社内プロキシのログ経由で URL が漏れれば、その 3 日間は認証なしで**全社員の提出物 ZIP** が取得可能である。

## 5. ライフサイクル

| ルール | 対象 | 設定 | 理由 |
|---|---|---|---|
| `expire-pending` | `pending/` | 7日で削除 | チェック不合格ファイルの一時退避。再提出されれば不要 |
| `expire-exports` | `exports/` | 3日で削除 | 配布用の一時生成物。**署名付きリンクの実質的な有効期限**を兼ねる |
| `submissions-archive-expire` | タグ `lifecycle=managed` の全オブジェクト | **60日で Deep Archive へ移行 / 365日で削除** | 提出物は提出直後〜翌月までしか参照されない。長期保管はコストを最小化しつつ、法定保存期間を意識して 1 年で廃棄 |

### ⚠️ Deep Archive 移行による運用影響（§6 課題2）

Deep Archive のオブジェクトは **`GetObject` が直接できない**（`InvalidObjectState`）。復元（Restore）操作を行い、数時間〜半日待つ必要がある。

本システムの一括DL は対象月の全オブジェクトを `get_object` で読んで ZIP 化するため、**60日を超えた月を一括DLするとエラーになる**。コードに復元処理は実装していない。

例：7月分の提出物は 2026-10 頃に Deep Archive へ移行し、以後 `一括DL 202607` が失敗する。

## 6. 既知の課題

| # | 深刻度 | 区分 | 内容 | 推奨対応 | 要否 |
|---|---|---|---|---|---|
| 1 | **中** | 機微情報 | `/dl` の署名に有効期限が無く、URL を知る者が認証なしでダウンロードできる。対象は `exports/` の ZIP・CSV＝**全社員の提出物や氏名一覧** | 署名対象に `exp`（失効時刻）を含め、`/bcast` と同じ方式（`hmac(uid:exp)`）に揃える。実装は数行。露出は現状 3 日に限定されているため即時ブロッカーではない | **早期対応推奨** |
| 2 | 中 | 運用 | 60日超の月の一括DL が Deep Archive により失敗する | ①保存期間の方針を見直して移行日数を延ばす、②`restore_object` と復元待ちの案内を実装する、のいずれか。**実際に7月分が失敗し始める前に判断が必要** | 早期判断 |
| 3 | 低 | 構成 | バケットが `RemovalPolicy.DESTROY` + `autoDeleteObjects`。スタック削除で提出物が全消去される | 本番運用を継続するなら `RETAIN` へ | 将来対応 |

---

## 7. 費用

保管量は 2026-09 時点で **数MB 程度**（提出物 9 件・テンプレ 5 件）。60日で Deep Archive（保管単価が約 1/20）へ移行するため、社員数が増えても保管費は小さい。費用面ではなく**個人情報の保持期間**の観点でライフサイクルを設計している。
